# 대여 전후 사진 비교

## 팀원 소개용 문구 (약 30초)

> 제가 맡은 기능은 대여 전후 사진에서 달라진 위치를 찾아주는 AI 비교입니다. 공개 모델인 LPIPS는 사람이 두 이미지를 보고 얼마나 다르게 느끼는지 학습한 모델입니다. 먼저 같은 물품의 두 사진을 정렬한 다음, LPIPS로 외관의 차이가 큰 영역을 찾아 반납 사진에 번호로 표시합니다. 빔프로젝터 예시에서는 반납 후 옆면에 생긴 사선 자국을 찾아냈습니다. 사용자는 표시된 곳을 원본과 대조해서 실제 손상인지 확인할 수 있습니다.

## 서비스 흐름

1. 공급자가 예약을 승인하고 품목별 대여 전 사진과 확인 항목을 등록합니다.
2. 대여자는 물품을 받고 수령을 확인합니다. 반납 시 각 부위의 기준 사진을 보며 동일한 부위를 촬영합니다.
3. 반납 요청은 사진과 함께 먼저 저장됩니다. 외관 비교가 가능한 부위는 순서대로 분석하고, 거래 상세의 ‘물품 상태 확인’에서 전후 사진과 확인 위치를 표시합니다.
4. 비교가 어려운 경우에도 요청은 유지됩니다. 대여자는 해당 부위를 다시 촬영할 수 있고, 공급자는 실물을 확인한 뒤 반납 완료 또는 문제 신고를 선택합니다. AI 결과가 거래를 자동 완료하거나 배상을 결정하지 않습니다.

개발용 단독 비교는 `/#dev/compare`, 반복 평가는 `/#dev/photo-evaluation`에 있습니다. 서비스 메뉴에는 이 경로를 노출하지 않습니다.

## 모델과 처리 과정

Richard Zhang 등이 CVPR 2018에서 발표한 **LPIPS**(Learned Perceptual Image Patch Similarity)의 공개 구현을 사용합니다. 앱은 SqueezeNet의 여러 층에서 추출한 특징과 LPIPS v0.1의 학습된 가중치로 위치별 차이 지도를 계산합니다. 별도 손상 데이터로 재학습하지 않았습니다. [논문 및 프로젝트](https://richzhang.github.io/PerceptualSimilarity/) · [공식 구현](https://github.com/richzhang/PerceptualSimilarity) · [구현 라이선스](https://github.com/richzhang/PerceptualSimilarity/blob/master/LICENSE)

OpenCV의 SIFT로 대응점을 찾고 RANSAC으로 이동·회전·크기 차이를 보정합니다. 대응점이 부족하거나 겹치는 면적이 좁으면 재촬영을 안내합니다. 겹치는 부분의 밝기를 보정하고 LPIPS 거리 지도에서 주변보다 차이가 큰 영역을 묶어 최대 6곳을 표시합니다. 번호는 차이가 큰 순서입니다. 위치 설명은 영역 좌표로 생성한 한국어 문구입니다.

긁힘 외에도 빛 반사, 그림자, 자세나 배경의 변화가 후보로 잡힐 수 있습니다. 임계값은 시연용이며 실제 대여 사진에서 정확도를 측정하지 않았습니다. 같은 면을 가까운 구도로 찍고 원본을 대조하세요. 미세한 흠집과 내부 작동 이상은 놓칠 수 있으므로 거래 분쟁 또는 배상 결정은 사람이 증빙을 확인합니다.

## 실행과 검증

[루트 실행 안내](../README.md)를 따릅니다. 서버는 로컬 컴퓨터에서 사진을 처리하며 거래·사진은 기존 데모처럼 브라우저에 저장됩니다. 모델 가중치는 최초 실행 시 `backend/.model-cache/`에 내려받습니다. 보정 가중치는 `lpips` 패키지에 포함됩니다.

```bash
backend/.venv/bin/python -m unittest discover -s backend -p 'test_photo_compare.py' -v
```

`POST /api/photo-comparison`에 `before`, `after` 두 이미지 파일을 multipart로 보냅니다. 응답은 `changes`(후보), `clear`(뚜렷한 후보 없음), `retake`(비교 곤란) 중 하나입니다. 좌표는 반납 사진 기준의 0~1 범위 `[x, y, 너비, 높이]`입니다.

## 거래 과정의 촬영 가이드와 품목별 점검

거래의 대여 전·반납 촬영 화면에 `getUserMedia()` 기반 카메라를 연결했습니다. 촬영 면을 선택하고 인도 사진을 찍은 뒤, 반납 때 기준 사진을 반투명하게 겹칩니다. 가이드 표시 여부와 투명도(10~80%)를 조절할 수 있습니다. 사진 사용 전에 다시 찍을 수 있으며, 촬영·취소·페이지 이동·탭 숨김 시 카메라 스트림을 종료합니다. 늦게 카메라 권한 요청이 완료돼도 이미 닫힌 화면에서는 스트림을 즉시 종료합니다.

가이드는 DOM 이미지이고 촬영은 영상 프레임만 Canvas에 그리므로 가이드가 저장 사진에 합성되지 않습니다. 앱에서 최초 생성한 PNG의 바이트와 촬영 시각·크기·선택 면을 기록합니다. 거래의 원본은 IndexedDB, 참조와 결과는 기존 localStorage에 저장합니다. 비교할 때는 원본 Blob을 전송하며 분석 서버가 별도 분석용 배열을 축소·정렬합니다. 거래 상세의 ‘원본 저장’으로 촬영 원본을 내려받을 수 있습니다. 카메라 선택을 이용한 일반적인 앱 내 촬영 흐름이며, 가상 카메라·재촬영·클라이언트 조작까지 막는 진본 증명은 아닙니다. 파일 업로드와 예시 선택은 개발용 비교 화면에서만 제공합니다.

새 거래는 품목별 여러 부위의 사진을 사용합니다. 드릴은 왼쪽·오른쪽·척·배터리 4부위, 프로젝터는 앞면·뒷면·왼쪽·오른쪽 4부위, 사다리는 전체·발판·힌지 3부위, 일반 물품은 앞면·뒷면·주요 사용 부위 3부위를 기본 목록으로 둡니다. 이는 초기 촬영 정책이며 실제 품목에 맞는 촬영 부담과 유효성을 검증해야 합니다. 등록 시 목록을 거래에 복사하여 이후 품목 설정 변경이 진행 중인 거래에 영향을 주지 않게 합니다.

텐트·타프·침낭·가방·의류는 보관 상태와 구성품 사진, 수동 점검을 적용하며 자동 외관 비교를 호출하지 않습니다. 보관 사진만으로 내부·설치 상태가 검증됐다고 표시하지 않습니다. 구성품·작동 확인 기록과 양측 단계의 상태 메모는 거래 상세에 함께 표시합니다. 현재 이름 기반 분류는 초기 정책으로, 등록 화면에서 점검 유형을 지정하는 기능과 상세 품목별 정책은 후속 과제입니다.

데이터는 `inspection.plan`, `before[viewId]`, `after[viewId]`, `results[viewId]`, 단계별 체크·메모에 기록합니다. `results`에는 실제 비교한 원본 참조를 함께 저장하여 사진이 바뀌면 오래된 결과를 표시하지 않습니다. 재촬영한 부위만 다시 분석하고 이전 반납 사진은 `returnHistory`에 참조를 보관합니다. 기존 단일 사진 거래는 한 부위로 읽으며 없는 부위를 생성하지 않습니다. 브라우저 저장소만 사용하는 시연이므로 서버 증빙 보관·기기 간 공유·접근 제어는 별도 구현이 필요합니다.

일반 사용자 UI에는 부위 선택, 상태 안내, 전후 사진과 위치 표시, 확대·원본 저장, 재촬영·반납 확인을 제공합니다. 처리 시간·모델명·비교 방식·실험 결과는 개발 도구에서만 표시합니다. 선택한 부위 이름과 SIFT 정합은 임의의 3차원 물품에서 동일 면을 보증하는 수단이 아닙니다.

전체 흐름은 **기본 화질 검사 → 특징 정합·정렬 → 변화 후보 표시**입니다. 화질 검사는 프레임 중앙 80%의 라플라시안 분산(12 미만), 어두운 픽셀(18 미만, 85% 초과), 밝은 픽셀(242 초과, 85% 초과) 비율을 사용합니다. 보류 시 어느 사진과 단계에서 중단했는지 한국어로 안내합니다. 임계값은 보수적인 개발 초기값으로, 물체 분할이나 가림·반사 검출을 수행하지 않습니다. 물품 재질·배경·해상도에 따라 오판할 수 있으므로 실제 촬영 자료로 조정해야 합니다.

### 반복 평가

`POST /api/photo-evaluation`은 동일 사진, 기존 빔프로젝터 시연 사진, 드릴의 합성 색상 자국, 위치 이동, 약한 밝기 변화, 심한 흐림, 심한 노출 부족, 심한 과다 노출, 다른 물품의 9건을 실행합니다. 동일한 품질 검사·정렬·밝기 보정을 사용하여 LPIPS와 픽셀 차이(채널 최대 차이 35 초과, 작은 영역 제거)를 비교합니다. 정렬이 미리 맞는 3건은 품질 검사·정렬·밝기 보정을 생략한 LPIPS 단독 비교도 실행합니다. 픽셀 차이는 단순 기준선이며 최적화한 손상 탐지 모델을 대표하지 않습니다.

화면은 기대 결과 일치 수, 목표 지점을 포함하는 후보 유무, 정상 사례의 오탐 수, 전체 보류 수와 건별 처리 시간을 표시합니다. 정상 사례가 보류되면 기대 결과 불일치로 계산합니다. 목표 지점 포함은 위치를 대략 확인하는 검사로, 영역 IoU·정밀도·실제 손상 검출률과 다릅니다. 서버 처리 시간은 업로드·다운로드 및 초기 모델 다운로드 시간을 제외합니다. 중복 평가 요청은 409로 거절합니다.

초기 실행 결과: LPIPS 전체 흐름 9/9, 픽셀 기준선 8/9, LPIPS 단독 3/3이 기대 결과와 일치했습니다. LPIPS는 지정 위치 2/2를 포함했고 정상 사례 오탐은 0/3, 비교 보류는 4/9입니다. [수치와 후보 좌표 기록](evaluation_reports/smoke-v1.json)은 브라우저에서 실행한 JSON에서 미리보기 이미지만 제외한 자료입니다. 모두 개발 중 확인한 자료와 인공 변형이므로 독립 검증셋 정확도나 실사용 성능으로 인용하면 안 됩니다. 실제 전후 손상, 같은 물품의 다른 면, 가림·반사·곡면 등의 검증은 남아 있습니다.

### 자동 검사

```bash
backend/.venv/bin/python -m unittest discover -s backend -p 'test_photo_compare.py' -v
npm --prefix frontend ci --ignore-scripts
npm --prefix frontend test
```

Python 검사는 후보 위치·정렬·밝기 보정, 저품질 사진의 모델 실행 차단, 단독 비교, API 유효성, 평가 잠금 해제를 확인합니다. 프런트 검사는 DOM과 가상 미디어 스트림으로 촬영 레이어 분리, 카메라 종료, 권한 거절, 권한 완료 후 취소 처리와 IndexedDB 원본 바이트 보존을 확인합니다. 실제 기기의 카메라 영상·브라우저별 권한·촬영 초점은 가상 테스트가 검증하지 않으므로 카메라가 있는 기기에서 별도 확인해야 합니다. 프런트 통합 검사는 가상 카메라로 다중 부위 인도·반납·비교 보류 후 요청 유지·부분 재촬영·이전 원본 참조 보관을 확인합니다. 별도 서비스 화면 검사에서는 기술 문구와 독립 비교 메뉴가 노출되지 않는지 확인합니다.

`POST /api/photo-comparison`에 `method=lpips|pixel`, `mode=pipeline|model-only`를 추가로 전달할 수 있습니다. 단독 비교는 분석용 배열의 가로·세로 크기가 같아야 합니다. 응답의 `stages`, `reason`, `failedPhoto`, `quality`, `durationMs`로 단계별 상태를 확인할 수 있습니다. 브라우저와 서버 양쪽 모두 현재 로컬 시연 환경입니다.
