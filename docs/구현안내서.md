# AI 물품대여 플랫폼 팀별 기능 구현 안내서

- 작성일: 2026-11-25
- 대상: 성진욱 및 팀원 3명
- 정책 기준: [확정 규칙](confirmed-rules.md)
- 현재 기준: 로컬 시연 코드. 화면이 존재해도 서버 연동·실제 모델 품질·운영 규칙 적용까지 완료했다는 의미는 아니다.

## 1. 담당 요약

16개 기능을 사용하는 화면과 데이터의 연결 관계에 따라 나누었다. **물품 등록 3단계 개선은 성진욱이 먼저 진행**한다. 팀원 1·2·3 표기는 실제 담당자 이름으로 바꾸어 사용할 수 있다.

| 담당 | 작업 영역 | 기존 목록 번호와 기능 |
| --- | --- | --- |
| 성진욱 | 등록 흐름 개선, 상태 점검·손상 분쟁 | ① 물품 등록 3단계 개선 / ⑪ 손상·분실 배상 / ⑫ 사진 비교 고도화 |
| 팀원 1 | 물품 탐색·등록 지원 | ⑦ 보증금 계산 / ⑬ 물품 추천 / ⑭ AI 등록·대여료 추천 |
| 팀원 2 | 예약·결제·반납 | ④ 예약 승인·만료 / ⑤ 예약 시각·요금 계산 / ⑥ 테스트 결제·정산 / ⑧ 취소·노쇼 / ⑨ 반납 자동 처리 / ⑩ 연장·연체료 |
| 팀원 3 | 채팅·프로필·구독 | ② 후기·프로필 평판 / ③ 읽지 않은 채팅 숫자 / ⑮ AI 채팅 추천 / ⑯ 구독 혜택 |

기능 수가 작업량을 뜻하지는 않는다. 사진 비교는 모델·데이터·촬영 UI가 함께 필요하고, 예약·결제는 거래 상태와 예외 처리가 많다. 작업은 작은 PR로 나누고 통합 가능한 단위부터 진행한다.

## 2. 성진욱 — 등록 흐름 개선·상태 점검·손상 분쟁

### ① 물품 등록 3단계 개선 — 우선 진행

**진행 상태:** 3단계 UI·연속 촬영·전체 사진 확인·부위별 재촬영을 로컬 작업 코드에 적용했다. 관련 프런트엔드 자동 검증 22개가 통과했으며, 카메라 동작은 모의 장치로 확인했다. 실제 모바일 기기 촬영과 팀 브랜치 통합은 추가 확인이 필요하다.

**주요 화면:** 물품 등록.

**해야 할 일**

- 한 화면에 길게 나열된 입력을 `기본 정보 → 사진 촬영 → 대여 조건`으로 나눈다.
- 기본 정보에서 물품명·카테고리·설명·거래 지역을 입력한다.
- 품목에 맞는 필수 부위를 차례로 직접 촬영한다. 촬영 후 다음 부위로 이동하고, 마지막에 전체 사진을 확인한다.
- 전체 확인에서 대표 사진 지정과 필요한 사진의 재촬영을 제공한다.
- 대여 조건에서 일일 대여료와 대여 가능 기간 등 기존 조건을 입력한다.
- 이전 단계 이동과 사진 재확인 시 입력값·사진을 유지하고, 필수 정보가 빠진 단계는 안내한다.
- 기존 사진 선택·업로드를 허용하지 않으며 촬영 원본 보관 흐름을 유지한다.

**완료 확인**

- 기본 정보 누락은 다음 단계 이동 전에 안내한다. 사진 미완료 상태에서도 대여 조건으로 이동할 수 있지만 사진 단계에는 완료 체크를 표시하지 않는다.
- 최종 게시 시 필수 사진이 없으면 촬영 미완료 안내를 표시하고 게시를 막는다. 촬영 단계로 돌아가도 입력한 대여 조건은 유지한다.
- 사진을 촬영할 때마다 등록 확인을 반복하지 않고 연속 촬영 후 전체를 확인한다.
- 도중 취소 시 촬영한 사진이 남고, 재촬영 취소 시 기존 사진이 사라지지 않는다.
- 재촬영하면 해당 사진만 교체되며 대표 사진 설정과 나머지 사진은 유지된다.
- 단계 이동·키보드 입력으로 게시가 의도치 않게 실행되지 않는다.

### ⑫ 사진 비교 고도화

**주요 화면:** 거래 상세의 대여 전 촬영·반납 촬영·상태 사진 확인.

**현재 기반:** 품목별 여러 부위 촬영, 대여 전 사진 반투명 가이드, 기초 품질 검사·정렬·손상 후보 표시가 있다. 실제 다양한 물품에서의 성능 검증은 별도이다.

**해야 할 일**

- 필요한 면이 선명하고 가려지거나 잘리지 않았는지 확인하는 검사를 보강한다.
- 전후 사진이 같은 부위인지 확인하고, 불확실하면 분석을 보류한다.
- 입체 물품은 대응 가능한 부위끼리 비교한다. 텐트 등은 구성품·직접 점검을 사용한다.
- 조명·각도·배경 변화와 실제 손상을 구분할 수 있는 시험 자료를 준비한다.
- 오탐·미탐·비교 불가율, 재촬영 빈도와 처리 시간을 기록한다.
- 서비스 화면에는 전후 사진과 확인할 위치를 표시하고, 개발용 모델·평가 설정은 별도 화면에서 다룬다.

**완료 확인**

- 흐림·다른 면·정렬 실패를 손상 또는 무손상으로 단정하지 않는다.
- 비교 불가여도 반납 요청은 유지되고 재촬영·공급자 확인으로 진행할 수 있다.
- 대표적인 실제 물품으로 유효한 경우와 실패하는 경우를 모두 설명할 수 있다.

### ⑪ 손상·분실 배상

**주요 화면:** 거래 상세 신고, 배상 협의, 관리자 분쟁 검토.

**현재 기반:** 손상·누락 신고와 관리자 의견 입력이 있다. 배상 금액·증빙·금전 처리 연결은 남아 있다.

**해야 할 일**

- 손상·분실 내용, 전후 증빙과 수리비 증빙을 접수한다.
- 수리 가능하면 증빙 수리비, 분실·수리 불가면 거래 당시 중고 가액을 상한으로 배상액을 협의한다.
- 당사자 합의와 관리자 검토 결과를 구분하여 기록한다.
- 신고 시 보증금 반환 보류를 결제 기능에 요청한다.
- 배상액이 보증금을 넘으면 추가 결제 동의를 요청하고, 거부·미결제는 미해결 분쟁으로 관리한다.

**연결:** 팀원 2가 금액을 실제로 처리한다. 이 담당은 신고·증빙·합의 결과를 관리하며 보증금 잔액을 별도로 수정하지 않는다. AI 결과만으로 책임·배상액을 확정하지 않는다.

## 3. 팀원 1 — 물품 탐색·등록 지원

### ⑦ 보증금 계산

**주요 화면:** 등록 마지막 단계, 물품 상세의 금액 안내.

**현재 구현:** 공급자가 입력한 현재 중고 가액에 플랫폼의 보증금 정책을 적용한다.

**해야 할 일**

- 공급자가 현재 중고 가액과 근거 자료를 입력할 수 있게 한다.
- 정해진 비율로 보증금을 계산하고 등록·상세 화면에서 일관되게 표시한다.
- 거래 시 가액과 보증금을 저장할 수 있도록 팀원 2에게 필요한 데이터를 제공한다.
- 정책 비율 변경이 이미 확정된 거래 금액을 바꾸지 않도록 연결한다.

**시연 정책:** 중고 가액의 30%를 원 단위로 반올림하고 최대 200,000원을 적용한다. 별도 최저액은 없다. 가액 근거 확인 절차는 결정 대기다.

### ⑬ 물품 추천

**주요 화면:** 홈 목록·검색 결과.

**현재 기반:** 검색·카테고리·가격·날짜 필터와 지역 우선 정렬이 있다. 개인화 추천 점수에 따른 정렬은 없다.

**해야 할 일**

- 사용자 조건과 물품 정보를 이용하여 추천 점수와 추천 순서를 계산한다.
- 대여 가능 날짜·예산 등 반드시 만족해야 할 조건은 추천 점수보다 먼저 적용한다.
- 이용 이력이 없는 신규 사용자에게도 추천 가능한 방식을 마련한다.
- 목록 추천 결과를 AI 채팅 담당에게 제공한다.

**완료 확인:** 같은 조건에서 결과를 재현할 수 있고, 대여 불가 물품을 가능한 물품처럼 추천하지 않는다. 추천 기준과 효과를 시험 사례로 설명할 수 있다.

### ⑭ AI 등록·대여료 추천

**주요 화면:** 등록 기본 정보·대여 조건.

**현재 기반:** 물품명에 따른 간단한 분류 규칙·고정 가격·문구 예시가 있다. 실제 시세 기반 대여료 모델은 아니다.

**해야 할 일**

- 물품명으로 카테고리와 게시글 초안을 제안한다.
- 시세·물품 상태·사용 이력·구매 시기를 입력받거나 확보할 데이터 구조를 마련한다.
- 중고 거래 가격을 일일 대여료로 바꾸는 근거와 계산·모델 방식을 검증한다.
- 추천 결과를 사용자가 확인·수정하여 적용하도록 한다.
- 자료가 부족하거나 모델 호출에 실패하면 근거 없는 가격을 확정값처럼 표시하지 않는다.

**완료 확인:** 고정 예시와 실제 모델 결과를 구분할 수 있고, 추천 가격의 입력값·근거를 확인할 수 있다.

**연결:** 등록 3단계 화면 구조는 성진욱이 먼저 변경한다. 이 담당은 각 단계에 들어갈 입력 항목·추천 결과를 기능별 모듈로 연결한다.

## 4. 팀원 2 — 예약·결제·반납

### ④ 예약 승인·만료

**주요 화면:** 대여 신청·공급자 승인·내 대여·거래 상세.

- 승인 즉시 예약 확정인 현재 흐름을 `신청 → 승인 → 결제 대기 → 결제 완료 → 예약 확정`으로 변경한다.
- 미응답 신청은 신청 후 12시간에 만료한다.
- 승인 후 결제 기한 1시간 동안 일정을 임시 확보하고, 미결제 만료 시 해제한다.
- 예약 중복은 서버 연결 시 동시 요청에서도 방지되어야 한다.

### ⑤ 예약 시각·요금 계산

**주요 화면:** 예약 날짜·시각 선택, 예상 금액.

- 시작·반납 날짜와 시각을 받는다.
- 기본 대여료는 24시간을 1일로 하고 남는 시간은 하루로 올린다.
- 신청·결제·거래 내역이 동일한 금액을 사용하도록 한다.

### ⑥ 테스트 결제·정산

**주요 화면:** 결제·거래 금액·환불·정산 내역.

- 실제 청구 없는 테스트 결제로 성공·실패·재시도 흐름을 구현한다.
- 기본 대여료·보증금·추가 대여료·연체료·배상액을 구분한다.
- 정상 반납 시 기본 대여료 정산과 보증금 반환을 처리한다.
- 같은 요청이 반복되어도 결제·환불·정산이 중복 반영되지 않도록 한다.
- 손상 분쟁·연체료 미결제·금액 이의가 있으면 보증금 반환만 보류한다.

### ⑧ 취소·노쇼

**주요 화면:** 거래 취소, 노쇼 신고, 관리자 확인.

- 인도 전 취소 시 기본 대여료·보증금을 전액 환불한다.
- 약속 시각에서 30분 이상 경과하고 연락을 시도해도 만나지 못하면 노쇼 신고를 받는다.
- 약속 일시·장소·연락 시도 기록을 접수하고 관리자 확정 후 취소·전액 환불·노쇼 기록을 적용한다.

### ⑨ 반납 자동 처리

**주요 화면:** 반납 요청·공급자 확인·거래 완료.

- 최초 반납 요청 시각과 공급자 확인 시각을 별도로 저장한다.
- 공급자 확인 또는 24시간 동안 이의 없음으로 실제 반납 시각을 확정한다.
- 이의 없는 24시간 경과 시 자동 완료·정산·반환을 처리하되, 보증금 보류 사유는 유지한다.
- 공급자가 늦게 확인했다는 이유로 연체료를 늘리지 않는다.

### ⑩ 연장·연체료

**주요 화면:** 거래 상세의 연장 요청·추가 결제·연체 내역.

- 다음 예약과 겹치지 않고 공급자 승인·추가 대여료 결제를 마친 경우에만 연장한다.
- 연체료는 `실제 반납일 - 반납 예정일`의 달력 날짜 차이에 일일 대여료를 곱한다.
- 예정일 당일 반납이면 시각이 늦어도 연체료는 0일분이다.
- 연체료 미결제·이의가 있으면 기본 대여료 정산과 보증금 보류를 구분한다.

**완료 확인**

- 결제 전 확정, 만료된 결제, 중복 예약, 반복 환불, 분쟁 중 보증금 반환을 막는다.
- 미응답·미결제·반납 자동 완료를 시계를 조절한 시험으로 확인한다.
- 기본 요금의 24시간 기준과 연체료의 달력 날짜 기준을 각각 확인한다.
- 브라우저 새로고침·서버 재시작 후에도 자동 처리 상태를 복구할 수 있도록 서버 저장과 연결한다.

**결정 대기:** 예약 수수료 적용 여부·부담 주체·요율은 미정이다. 금액 처리에 임의 수수료를 추가하지 않는다.

## 5. 팀원 3 — 채팅·프로필·구독

### ② 후기·프로필 평판

**주요 화면:** 거래 완료 후 후기, 내 정보·상대방 프로필.

**현재 기반:** 완료 거래에서 대여자만 후기 작성이 가능하다.

- 대여자·공급자가 서로 평가하도록 작성 권한과 저장 구조를 변경한다.
- 거래 완료 후 7일간 작성 가능하게 한다.
- 양쪽이 모두 작성하거나 7일이 지나면 공개한다. 공개 전에는 상대에게 보여주거나 별점 집계에 포함하지 않는다.
- 프로필에 평균 별점·후기 수·완료 거래 수를 표시한다.

**완료 확인:** 거래 당사자만 완료 거래를 평가하고, 한쪽 작성 상태·기한 경과·양쪽 작성 상태의 공개와 집계가 규칙과 일치한다.

### ③ 읽지 않은 채팅 숫자

**주요 화면:** 하단 채팅 탭·채팅방 목록·대화방.

- 받은 메시지의 읽음 기록을 관리한다. 내가 보낸 메시지는 집계에서 제외한다.
- 하단 탭에는 전체 합계, 각 방에는 방별 숫자를 표시한다.
- 채팅방이 열려 있고 해당 메시지가 실제 화면에 보일 때만 읽음 처리한다.
- 앱이 배경이거나 화면이 꺼져 있으면 읽음 처리하지 않는다.
- 상대가 내 메시지를 읽었는지 보여주는 표시는 이번 범위에 추가하지 않는다.

**완료 확인:** 다른 방 도착, 스크롤 밖 메시지, 앱 배경 전환, 재접속 후 숫자가 올바르다. 실제 다중 사용자 검증에는 서버 저장·실시간 전달 연결이 필요하다.

### ⑮ AI 채팅 추천

**주요 화면:** AI에게 물어보기·추천 물품 카드.

**현재 기반:** 대화 화면과 로컬 모델 호출 API가 있다. 실제 모델 실행·답변 품질은 별도 확인이 필요하다.

- 무료 모델 실행 환경을 연결하고 이용 목적·예산·날짜에 따른 물품 추천을 제공한다.
- 팀원 1의 물품 검색·추천 기능을 사용하여 실제 존재하는 물품을 카드로 표시한다.
- 모델 미설정·시간 초과·잘못된 답변·추천 가능한 물품 없음 등의 상태를 처리한다.
- 답변 생성만으로 예약·결제·물품 정보를 변경하지 않는다.

**완료 확인:** 없는 물품을 정상 카드로 만들지 않고, 실제 모델로 응답 시간·추천 적합성·실패 처리를 확인한다.

### ⑯ 구독 혜택

**주요 화면:** 구독 안내·내 혜택·홍보권 사용·반납 픽업 신청.

**현재 기반:** 혜택 안내 화면만 있다.

- 구독 상태와 혜택 사용 내역을 관리한다.
- 월간 게시글 홍보권 지급·사용·잔여량 확인을 연결한다.
- 예약 수수료 정책이 확정되면 할인 적용 자격을 결제 담당에게 제공한다.
- 반납 픽업 신청과 진행 상태를 관리한다.
- 여러 물품을 빌려주는 기능 자체는 기본 이용자에게도 제공한다.

**결정 대기:** 구독 요금·홍보권 횟수·할인율·픽업 지역·횟수·비용·운영 주체는 미정이다. 화면의 예시값을 확정 정책으로 사용하지 않는다.

## 6. 담당 간 연결 기준

다음 표는 담당 경계이다. 실제 필드명·함수명·API 경로는 개발 전에 함께 맞춘다.

| 연결 | 제공할 정보 | 담당 경계 |
| --- | --- | --- |
| 물품 → 예약 | 물품 ID, 공급자, 일일 대여료, 확정할 중고 가액·보증금, 가능 기간 | 팀원 1이 물품 정보를 제공하고 팀원 2가 거래 시점 값을 저장한다. |
| 등록 화면 → AI 등록 지원 | 현재 입력값, 분류·초안·추천 가격, 오류 상태 | 성진욱이 단계 화면을 만들고 팀원 1이 지원 기능을 연결한다. |
| 사진 점검 → 반납 | 거래·부위별 사진, 촬영 시각, 비교 가능 여부와 결과 | 성진욱이 상태 점검을 관리하고 팀원 2가 거래 반납 상태를 변경한다. |
| 손상 분쟁 → 결제 | 신고·합의·검토 결과, 보류 사유, 합의 금액 | 성진욱이 분쟁 결과를 제공하고 팀원 2가 금액 처리를 수행한다. |
| 거래 완료 → 후기 | 거래 당사자, 완료 여부·완료 시각 | 팀원 2가 거래 상태를 제공하고 팀원 3이 후기 기한·공개·집계를 관리한다. |
| 물품 추천 → AI 채팅 | 조건에 맞는 실제 물품 목록·추천 순서 | 팀원 1이 추천 데이터를 제공하고 팀원 3이 대화와 카드를 표시한다. |
| 구독 → 홍보·할인 | 구독 상태·혜택 잔여량·사용 결과 | 팀원 3이 자격·사용 내역을 관리하고 팀원 1·2가 해당 기능에 적용한다. |

거래 상태, 결제 상태, 점검 결과와 분쟁 상태는 서로 구분하여 관리한다. 각 기능이 같은 상태를 서로 다른 의미로 덮어쓰지 않도록 한다.

## 7. 공통 작업과 협업 방법

### 공통 담당을 별도로 정해야 하는 작업

- 회원가입·로그인 및 서버에서의 권한 검증.
- 데이터베이스, 원본 사진 저장소, 거래·결제·후기 저장 API.
- 실시간 메시지 전달·알림 기반과 서버 배포.
- 서버에서 수행하는 만료·자동 완료 작업과 재시작 복구.

위 작업은 현재 로컬 저장 기반 시연을 실제 다중 사용자 서비스로 연결하기 위한 공통 기반이다. 네 사람 중 누가 맡는지는 아직 정하지 않았으며, 각 기능의 UI와 데이터 연결 지점을 먼저 분명히 한다.

### 브랜치·PR

1. 공통 개발 기준은 `develop`이다. 각자 최신 `develop`에서 작업 브랜치를 만든다.
2. 기능별 파일로 나누어 작업한다. 현재 공통 화면·이벤트 파일에 코드가 모여 있으므로 공통 부분을 변경할 때에는 담당 간에 미리 알린다.
3. 하나의 큰 PR보다 화면·규칙·연동 등 검토 가능한 단위로 나누어 `develop`에 PR을 보낸다.
4. PR에 변경 내용, 확인 방법·결과와 화면 변경 스크린샷을 포함한다. 기존 README의 리뷰 절차를 따른다.
5. `main`을 이번 개발 통합 대상으로 사용하지 않는다.

### 제출할 내용

- 담당 화면과 동작하는 기능.
- 정상 흐름과 주요 실패·예외 흐름의 확인 결과.
- 다른 담당자가 사용할 데이터·함수·API 설명.
- 실제 구현한 범위, 아직 예시인 범위와 결정 대기 항목.

후기 수정·삭제, 분쟁 처리 기한, 품목별 세부 촬영 목록 등 미정 사항은 [확정 규칙 문서의 보류 항목](confirmed-rules.md#17-보류-항목과-추가-명세가-필요한-경계)을 확인한다. 확정되지 않은 정책을 각자 다르게 정하지 않는다.
