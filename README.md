## 팀 시연용 Firestore DB

공용 주소로 팀 시연을 하려면 [Cloud Run 배포 안내](backend/README-cloud-run.md)를 참고하세요.

물품, 대여 거래, 거래 채팅, 알림을 Firestore에 저장하려면 [DB 실행 및 연결 안내](backend/README-firestore.md)를 따르세요. 프로젝트가 없어도 로컬 에뮬레이터에서 같은 화면으로 등록과 조회를 시험할 수 있습니다.

## 렌토 UI 실행

대여 전후 사진 비교까지 시연하려면 Python 3.12에서 저장소 루트를 기준으로 아래 명령을 실행합니다.

```bash
python3.12 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements-compare.txt
backend/.venv/bin/python backend/compare_server.py --port 8092
```

Windows에서는 가상환경을 `py -3.12 -m venv backend/.venv`로 만들고 Python 실행 경로를 `backend/.venv/Scripts/python.exe`로 바꿉니다. 첫 기동 때 PyTorch 공식 서버에서 SqueezeNet 가중치 약 5MB를 받아 캐시합니다. [개발용 사진 비교](http://localhost:8092/index.html#dev/compare)에서 빔프로젝터 예시 또는 직접 촬영한 사진 두 장을 선택하세요. [모델 설명과 발표 문구](backend/README.md)

기존 프런트엔드만 보려면 `python3 -m http.server 8000 --directory frontend`로 실행할 수 있습니다. 사진 비교 API는 위의 Python 앱에서 제공합니다.

### 거래 과정의 상태 사진

- **내 정보 → 대여 내역 → 내 대여 → 물품 카드**에서 상태 사진을 확인합니다. 마이페이지의 독립 사진 비교 메뉴는 제거했습니다.
- 공급자는 예약 확정 후 **대여 전 사진 촬영**, 대여자는 수령 확인 후 **반납 사진 촬영**으로 진입합니다. 새 거래는 드릴 4부위, 프로젝터 4부위, 사다리 3부위, 일반 물품 3부위를 기본으로 촬영합니다. 품목별 목록은 `frontend/src/inspection.js`에서 관리합니다.
- 반납 촬영에는 각 부위의 대여 전 사진을 반투명 가이드로 보여줍니다. 각 부위의 사진과 구성품·작동 확인을 모두 등록하면 반납을 요청합니다. 비교 결과가 보류돼도 반납 요청은 유지되며 재촬영 또는 공급자 직접 확인으로 마무리합니다.
- 텐트·타프·침낭 등은 보관 상태와 구성품 사진, 직접 확인 항목을 사용합니다. 이 유형의 사진에 자동 손상 판정을 수행하지 않습니다.
- 거래 상세는 부위 선택, 전후 사진, 확인이 필요한 위치, 사진 확대·원본 저장, 구성품 확인 기록과 상태 메모를 제공합니다. 모델명·처리 시간·평가 설정은 표시하지 않습니다. 재촬영한 부위만 다시 비교하며 이전 반납 사진 참조도 보관합니다.
- 기존 단일 사진 거래는 실제 남아 있는 사진을 유지합니다. 여러 면 촬영 목록은 새 거래부터 적용합니다.
- 카메라는 `localhost` 또는 HTTPS와 사용자 권한이 필요합니다. 촬영 원본은 브라우저 IndexedDB에 저장합니다. 기본 모드는 거래·결과를 localStorage에 저장하고, Firestore 모드는 서버의 DB에 저장합니다.
- 개발 도구는 사용자 메뉴에 연결하지 않으며 `/#dev/compare`, `/#dev/photo-evaluation`로 직접 접근합니다. 경로 구분은 인증·권한 제어를 대신하지 않습니다. 기존 `/#compare`는 대여 내역으로 이동합니다.

검증 명령과 모델 평가 해석은 [사진 비교 구현 안내](backend/README.md)를 참고하세요.

- `frontend/`에는 홈, 물품 등록·상세, 대여 거래, 채팅, 구독 안내 화면과 샘플 데이터가 있습니다.
- `backend/`는 전후 사진 비교 API와 시연용 웹 서버를 제공합니다.
- **내 정보 → 데모 프로필 전환**에서 대여자, 공급자, 관리자를 전환할 수 있습니다. 신청과 사진 등 시연 데이터는 같은 브라우저에 저장됩니다.
- 개발용 비교 화면의 빔프로젝터 예시로 변화 후보를 확인할 수 있습니다. 실제 거래의 촬영 양식에는 예시 선택과 파일 업로드를 제공하지 않습니다.

## 브랜치

- 팀에서 미리 만드는 공용 개발 브랜치는 `develop` 하나입니다.
- 각 팀원은 작업을 시작할 때 최신 `develop`에서 자신의 작업 브랜치를 만듭니다. `develop`에 직접 푸시하지 않고 PR로 변경을 반영합니다.
- 브랜치는 작업 하나당 하나씩 만듭니다. 이름은 `유형/이슈번호-짧은-설명` 형식으로 작성합니다.

| 유형 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat/12-rental-request` |
| `fix` | 버그 수정 | `fix/24-booking-conflict` |
| `docs` | 문서 변경 | `docs/8-update-readme` |
| `refactor` | 동작을 유지하면서 코드 구조 개선 | `refactor/30-rental-service` |

```bash
git fetch origin
git switch develop
git pull --ff-only
git switch -c feat/12-rental-request
```

## Pull Request

1. 작업 브랜치에서 `develop`으로 PR을 엽니다. 제목에 변경 내용을 적습니다. 예를 들어 `대여 신청 기능 추가`처럼 작성합니다.
2. 본문에 변경 내용과 테스트 방법·결과를 적습니다. 관련 이슈가 있으면 `#12`처럼 연결합니다. 화면을 변경했다면 스크린샷을 첨부합니다.
3. **작성자 외 팀원 1명 이상이 승인**하고, 변경 요청을 모두 해결한 뒤 병합합니다. 충돌이 있으면 작업 브랜치에서 해결하고 다시 확인합니다. 자동 검사가 설정되어 있으면 통과 여부도 확인합니다.
4. 병합이 끝나면 작업 브랜치를 삭제합니다.
